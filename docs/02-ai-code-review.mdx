# AIコードレビューとは何か

## この章の目的

従来のコードレビューが抱える課題を確認し、AIコードレビューがどこを支援できるのかを理解します。

また、AIコーディングで生成したコードをそのままプルリクエスト（Pull Request。以下PR）に出すのではなく、自分自身でAIレビューを使って確認する重要性も学びます。

## 従来レビューの課題

コードレビューは重要ですが、チーム開発ではいくつかの課題が起こりやすくなります。

- レビュー待ちが発生する
  PRを作成しても、レビュアーが別の作業をしていると確認が始まるまで時間がかかります。小さな修正でも待ち時間が長くなると、開発の流れが止まりやすくなります。

- レビュアーの負担が大きい
  レビュアーは、変更されたコードを読み、何のための変更かを理解し、ほかの機能に影響しないかを考える必要があります。変更量が多い場合や、説明が少ない場合は、レビューする側の負担が大きくなります。

- レビューの観点が人によって変わる
  経験豊富な人は、コードの作り方や影響範囲まで見られます。しかし、忙しいと細かく確認できないこともあります。また、レビュアーによって気づく点が違うため、指摘の内容にばらつきが出ることもあります。

これらの課題は、レビューそのものが不要という意味ではありません。人間が見るべき重要な判断に集中するために、機械的に確認できる部分や初期確認を支援する仕組みが必要になります。

## AIコードレビューで変わること

AIコードレビューとは、AIがPRや変更されたコードを読み、レビューを支援する仕組みです。

AIレビューを使うと、PRを作成した直後にフィードバックを得られます。人間のレビュアーを待つ前に、自分の変更を見直すきっかけを得られます。

たとえば、PRの内容を要約してもらうと、レビュアーは全体像をつかみやすくなります。また、実装者自身も「説明が足りているか」「変更範囲が広すぎないか」を確認しやすくなります。

これにより、人間のレビュアーは「そもそもこの仕様でよいか」「この作り方で今後も変更容易性を保てるか」「ユーザーにとって問題がないか」といった、人間の判断が必要な部分に時間を使いやすくなります。

AIレビューは、人間レビューを置き換えるものではありません。レビューの入口で品質を底上げし、人間レビューを始めやすくするための支援と考えると理解しやすくなります。

## AIコーディングとの関係

AIコーディングでは、AIにコード生成、コードの整理、テスト作成、バグ修正などを依頼できます。短時間で多くのコードを作れるため、開発速度を上げやすい一方で、生成されたコードをそのまま信頼するのは危険です。

AIが生成したコードには、次のような問題が含まれることがあります。

- 一見動きそうだが、要件の一部を満たしていない
- 既存のコードの書き方に合っていない
- エラーが起きたときの考慮が不足している
- 力技で動かしていて、可読性や変更容易性が低い
- 環境変数や入力値にフォールバックを用意した結果、値が存在しない場合のエラーが出なくなり、不具合が見つかりにくくなる
- 使っていない処理や、必要以上に複雑な作りが混ざっている
- 正常に動く場合のテストは多いが、空の値や上限・下限などの境界値のテストが不足している

つまり、AIコーディングでコードを書く力が増えるほど、レビューの重要性も高まります。作る速度だけが上がって確認が追いつかないと、品質の低い変更が増えてしまいます。

AIコードレビューは、AIコーディングで生まれたコードを確認するための相性のよい仕組みです。生成AIに実装を手伝わせ、別の観点でAIレビューに確認させることで、開発者は「何のための変更か」「ほかの機能に影響しないか」「テストは足りているか」を見直しやすくなります。

## セルフAIレビューの重要性

セルフAIレビューとは、人間のレビュアーに依頼する前に、実装者自身がAIレビューを使って自分の変更を確認することです。

AIコーディングを使った場合は、特にセルフAIレビューが重要です。AIが生成したコードを「AIが書いたから大丈夫」と考えるのではなく、「自分が責任を持つコードとして確認する」必要があります。

セルフAIレビューは、自分で書いたコードに対しても有効です。自分で書いたコードは、無意識のうちに「正しいはずだ」と考えやすくなります。このような思い込みがあると、ちょっとしたタイポや条件分岐のミスを見落としやすくなります。

AIレビューを第三者の視点として使うと、自分では見落としていた小さなミスに気づきやすくなります。人間のレビュアーに依頼する前に、自分の変更を一度客観的に見直すための手段として役立ちます。

PRを出す前にセルフAIレビューを行うと、次のような効果があります。

- 明らかなミスを事前に修正できる
- PRの説明に不足している情報に気づける
- テストの追加や確認観点を整理できる
- 人間レビュアーの負担を減らせる
- レビューコメントのやり取りを本質的な議論に集中できる

セルフAIレビューでは、AIの指摘をすべて受け入れる必要はありません。大切なのは、指摘をきっかけに「この変更はなぜ必要か」「この実装で十分か」「ほかの機能に影響しないか」を自分で考えることです。

AIコーディングでは、実装者の役割が「すべてを手で書く人」から「AIの出力を読み、判断し、品質に責任を持つ人」へ広がります。セルフAIレビューは、その責任を果たすための基本的な習慣です。

## AIレビューと人間レビューの役割分担

AIレビューと人間レビューは、得意な領域が異なります。

AIは、変更されたコードを素早く読み、一般的な観点から気になる点を挙げることが得意です。たとえば、使っていない変数、値がない場合の扱い、エラー処理の不足、テスト不足の可能性、複雑すぎる処理などを指摘できます。

一方、人間は、プロダクトの目的、ユーザーへの影響、チームの優先度、組織固有の事情を踏まえた判断が得意です。AIが「この実装は複雑です」と指摘しても、その複雑さが業務要件上必要な場合もあります。最終的な判断は人間が行う必要があります。

役割分担の考え方は、次のように整理できます。

| 担当 | 主な役割 |
| --- | --- |
| AIレビュー | 変更内容の要約、初期確認、一般的なリスクの指摘、修正案の提示 |
| 実装者 | AIの指摘を確認し、必要な修正を行い、変更の意図を説明する |
| 人間レビュアー | 要件、設計、優先度、プロダクト判断、最終的な承認を行う |

AIに任せる部分と、人間が判断する部分を分けることで、レビュー全体の効率と品質を高められます。

## AIレビューの得手不得手

AIレビューには得意なことと不得意なことがあります。AIの指摘は便利ですが、常に正しいとは限りません。何を任せやすく、何を人間が判断すべきかを分けて考えることが大切です。

### 得意なこと

AIレビューが得意なのは、変更されたコードから一般的なリスクを見つけたり、読み手の理解を助けたりすることです。

たとえば、明らかな不具合の可能性を指摘できます。条件分岐の抜け、データが空の場合の扱い、エラーが起きたときの処理、返す値の間違いなどです。

また、見落としやすいケースの確認にも役立ちます。正常に動く場合だけでなく、入力が空の場合、通信に失敗した場合、権限がない場合、データが存在しない場合などを挙げられます。

AIは修正案を提示できることもあります。単に「問題があります」と言うだけでなく、「このように直すとよさそうです」という形で具体例を出せるため、初学者にとって学びやすいフィードバックになります。

### 不得意なこと

AIレビューにも限界があります。

特に苦手なのは、コードだけでは判断できないことです。たとえば、仕事上の優先度、顧客との約束、プロダクト方針、チーム内だけで共有されている事情などは、変更されたコードだけを読んでも正しく判断できません。

また、AIの指摘が常に正しいとは限りません。問題ではない箇所を問題のように指摘することもあれば、本当に重要なリスクを見落とすこともあります。修正案も、既存の設計やプロジェクトの方針に合わない場合があります。

そのため、AIレビューを使うときは次の姿勢が大切です。

- AIの指摘を鵜呑みにしない
- 指摘の理由を確認する
- プロジェクトの文脈に合うかを判断する
- 必要であれば人間に相談する
- 最終的な責任は実装者とチームが持つ

AIコードレビューは、レビューの質を高める強力な支援です。しかし、判断を丸投げするものではありません。AIからのフィードバックを材料として使い、人間が意図と責任を持ってコードを改善することが重要です。
