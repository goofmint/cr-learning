# コードレビューとは何か

## この章の目的

コードレビューを、単なるバグ探しではなく、品質、設計、知識共有、チーム開発を支える活動として理解します。

## コードレビューとは

コードレビューとは、ある人が書いたコードを、別の人が確認する活動です。

レビューでは、コードを読んで、変更の目的に合っているか、読みやすいか、あとから直しやすいか、ほかの機能に悪い影響を与えそうな点がないかを確認します。

たとえば「ブックマークを保存する機能」を追加した場合、レビューでは次のような点を見ます。

- 業務要件や完了要件を満たしているか
- エラーが起きたときの考慮が抜けていないか
- 変数名や関数名から意味が伝わるか
- 同じような処理が重複していないか
- 将来の変更で壊れやすい書き方になっていないか

つまりコードレビューは、コードをチームで安全に育てていくための確認作業です。

## なぜコードレビューを行うのか

コードレビューの目的は、大きく3つあります。

1つ目は、変更の品質を高めることです。実装者が気づかなかった考慮漏れ、入力値の扱い、例外時の扱い、既存コードとの不整合などを、別の視点から確認できます。

2つ目は、変更の妥当性を確認することです。コードが正しく動いていても、そもそも業務要件や完了要件に合っていない場合があります。レビューでは「この実装で本当に解決したい問題を解決できているか」を確認します。

3つ目は、保守しやすい状態を保つことです。ソフトウェアは一度作って終わりではありません。機能追加や修正を何度も重ねていくため、読みやすく、変更しやすく、組織のコーディング規約に沿ったコードにしておく必要があります。

## レビューとテストの違い

レビューというと、まず「バグを見つけること」を想像しがちです。しかし、不具合の検出は本来テストの領域です。

レビューを通ったからといって、不具合がないと判断するのは危険です。テストでは、入力と出力、画面操作、APIの応答、エラー時の動きなどを実際に確認します。一方、レビューでは、コードを読んで「この変更は目的に合っているか」「見落としやすいリスクはないか」「保守しやすい形になっているか」を確認します。

レビューとテストは、どちらか一方で置き換えるものではありません。レビューで設計や読みやすさを確認し、テストで動作を確認することで、変更の信頼性を高めます。

## コードレビューで確認すること

レビューでは、次のような観点を確認します。

- **可読性**  
  ほかの人が読んで理解しやすいか

- **設計**  
  役割の分け方や処理の置き場所が自然か

- **規約と一貫性**  
  社内や組織のコーディング規約、既存のコードの書き方に合っているか

- **要件との一致**  
  業務要件、仕様、完了要件を満たしているか

- **連携部分**  
  バックエンドとフロントエンド・アプリの間で、必要なデータが正しく送受信されるか

- **影響範囲**  
  ほかの機能を壊す可能性がないか

- **運用リスク**  
  エラー時や想定外の入力に対応できるか

- **変更しやすさ**  
  将来の機能追加や修正がしやすいか

初学者のうちは、すべてを完璧に見る必要はありません。まずは「自分以外の人がこのコードを読んだときに困らないか」という視点を持つことが大切です。

## レビューは知識共有でもある

コードレビューは、指摘を受ける場であると同時に、学び合う場でもあります。

レビューのやり取りを通じて、チーム内に次のような知識が共有されます。

- 機能の仕様や背景
- なぜその設計にしたのか
- プロジェクトでよく使う書き方
- 避けたほうがよい実装パターン
- テストやエラー処理で気をつける点

実装者は、自分では気づけなかった考え方を学べます。レビュアーも、変更内容を読むことでプロダクトやコードベースへの理解を深められます。

このように、レビューは個人の作業をチームの知識に変える役割を持っています。

## レビューで確認する主な観点

レビューでは、コードをなんとなく読むのではなく、観点を分けて確認すると考えやすくなります。

| 観点 | 確認すること |
| --- | --- |
| 目的 | 変更の目的、業務要件、完了要件に合っているか |
| 動作 | 正常時とエラー時の動作をテストで確認できる状態か |
| 読みやすさ | 名前、処理の流れ、コメントが分かりやすいか |
| 規約 | 社内や組織のコーディング規約に沿っているか |
| 保守性 | 将来の変更に耐えられる構造か |
| 連携 | バックエンドとフロントエンド・アプリのデータ送受信が成り立つか |
| テスト | 重要な動きがテストで確認されているか |
| 影響範囲 | 既存機能に悪影響がないか |

レビューでは、細かい書き方だけに集中しすぎないことも重要です。インデントや命名も大切ですが、まずは「要件に合っているか」「壊れやすくないか」「読み手が理解できるか」を優先して確認します。

## コードレビューの考え方を学ぶ参考資料

コードレビューのあり方を学ぶ参考資料として、GoogleのEngineering Practicesに含まれる「[コードレビューの基準](https://fujiharuka.github.io/google-eng-practices-ja/ja/review/reviewer/standard.html)」があります。

このガイドラインでは、コードレビューの目的を、コードベース全体の健康状態を時間をかけて改善することだと説明しています。また、完璧なコードを求めて変更を止め続けるのではなく、全体として保守性、可読性、理解しやすさが改善するかを見て判断する考え方が示されています。

初学者にとって大切なのは、レビューを「細かい間違い探し」として捉えないことです。変更を前に進めながら、コードベースを少しずつよくしていく活動として考えると、レビューの目的が理解しやすくなります。

## レビューは協力してよくするための活動

コードレビューは、相手の間違いを責めるための活動ではありません。より良いコードにするために、チームで確認し合う活動です。

そのため、レビューコメントでは「なぜ気になったのか」「どう直すとよさそうか」を伝えると、受け取る側が判断しやすくなります。

たとえば、単に「ここはよくないです」と書くよりも、「この関数は複数の役割を持っているので、保存処理と表示用の整形処理を分けると読みやすくなりそうです」と書くほうが、次の行動につながります。

レビューを受ける側も、指摘を個人への批判として受け取る必要はありません。分からない点があれば質問し、必要であれば実装の意図を説明します。

良いレビューは、コードだけでなく、チームの開発の進め方も少しずつよくしていきます。
